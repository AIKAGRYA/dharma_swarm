# The Agentic Internet Trust Stack — as of July 2026

**Research question:** Who answers under whose authority an agent acts, and what's missing? A map of existing protocols and efforts against a proposed constitutional/accountability layer answering five questions: (1) **authority** — under whose authority the agent acts; (2) **material burden** — what obligation/cost/risk it creates; (3) **telos** — what purpose it serves; (4) **evidence** — what proves results; (5) **challenge/reversal** — who can contest or undo an action.

**Method:** Primary sources fetched directly (specs, EIPs, official blogs, GitHub repos, arXiv). Every factual claim carries a markdown link to the fetched source. "n.a." marks unconfirmable items. Date of research: 11 July 2026.

**Layer taxonomy used below:** identity · delegation · payment · communication · evidence/provenance · governance · discovery/reputation · observability.

## 1. MCP — Model Context Protocol

- **What it is.** A standardized way for LLM applications (hosts/clients) to connect to servers that expose tools, resources, and prompts, using JSON-RPC 2.0 over stateful connections ([MCP spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18)). It covers the **communication** layer between a model host and its tools/data.
- **Who governs it.** MCP is now formally governed as **"Model Context Protocol a Series of LF Projects, LLC"** (i.e., under the Linux Foundation umbrella); governance changes must also be approved by LF Projects, LLC ([MCP Governance](https://modelcontextprotocol.io/community/governance)). Structure is a **Steering Group** of Maintainers, Core Maintainers, and **Lead Maintainers** — the last being final decision-makers, explicitly described as **BDFL ("Benevolent Dictator for Life")** ([MCP Governance](https://modelcontextprotocol.io/community/governance)). Membership is individual, not corporate; no company seats. Spec changes go through **SEPs (Specification Enhancement Proposals)** ([MCP Governance](https://modelcontextprotocol.io/community/governance)). Anthropic is not named on the governance page ([MCP Governance](https://modelcontextprotocol.io/community/governance)).
- **Current version / status (2026).** Current dated spec revision is **`2025-06-18`** ([MCP spec](https://modelcontextprotocol.io/specification/2025-06-18)).
- **Auth model (OAuth).** Authorization is **OPTIONAL** and defined for HTTP transports. The MCP server acts as an **OAuth 2.1 resource server**; the client is an OAuth 2.1 client; a separate or co-hosted **authorization server** issues tokens ([MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)). It mandates: OAuth 2.1 with PKCE, **Protected Resource Metadata (RFC 9728)** for AS discovery via `WWW-Authenticate` on 401, **Authorization Server Metadata (RFC 8414)**, **Resource Indicators (RFC 8707)** — clients MUST send `resource` in auth and token requests to bind the token audience to a specific MCP server — and SHOULD support **Dynamic Client Registration (RFC 7591)** ([MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)). Token passthrough to upstream APIs is explicitly forbidden to prevent confused-deputy attacks ([MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)).
- **What it does NOT cover.** No payment mechanism, no agent-to-agent messaging (that is A2A), no delegation-chain semantics (who authorized the human/agent principal), no persistent agent identity, no evidence/audit-receipt of what the agent did. Auth binds a token to a *resource*, not to a *chain of delegated authority*. Consent is per-tool-invocation at the host UI, not a durable, verifiable record ([MCP spec](https://modelcontextprotocol.io/specification/2025-06-18); [MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)).
- **Layers covered:** communication; partial identity (via OAuth resource/token binding).

## 2. A2A — Agent2Agent Protocol

- **What it is.** An open standard for communication/collaboration between agents built on diverse frameworks, spanning remote agents, local agents, and humans; JSON-RPC / gRPC / HTTP+JSON bindings ([A2A home](https://a2a-protocol.org/latest/); [A2A spec](https://a2a-protocol.org/latest/specification/)).
- **Who governs it.** Originally Google; **donated to the Linux Foundation**, maintained by a **Technical Steering Committee** with representatives from AWS, Cisco, Google, IBM Research, Microsoft, Salesforce, SAP, ServiceNow; Apache-2.0 ([A2A home](https://a2a-protocol.org/latest/)).
- **Current version / status (2026).** The spec identifies protocol versions by Major.Minor, with `0.3` and `1.0` shown as active/compatible; clients send an `A2A-Version` header, and unsupported versions return `VersionNotSupportedError` ([A2A spec](https://a2a-protocol.org/latest/specification/)).
- **AgentCard.** A JSON metadata document (discoverable at `/.well-known/agent-card.json`) declaring identity (`name`, `description`, `provider`, `version`), `skills`, `supportedInterfaces`, `capabilities`, and **`securitySchemes`/`securityRequirements`** (API key, HTTP auth, OAuth2, OpenID Connect, mutual TLS) ([A2A spec](https://a2a-protocol.org/latest/specification/)). AgentCards **MAY be signed with JWS** (canonicalized via JCS/RFC 8785), giving a verifiable card-integrity signature ([A2A spec](https://a2a-protocol.org/latest/specification/)).
- **Extensions.** Declared via `capabilities.extensions` (`AgentExtension` with `uri`, `required`, `params`); clients opt in via `A2A-Extensions`; extension governance uses a **tiered promotion process** ([A2A spec](https://a2a-protocol.org/latest/specification/); [A2A home](https://a2a-protocol.org/latest/)). AP2's payment support is delivered as an A2A extension (the **A2A x402 extension**) — see §3–4.
- **Delegation/authority.** A2A supports **in-task authorization** by moving a task to `TASK_STATE_AUTH_REQUIRED`, delegating fulfillment of that authorization to the client, which may itself be an A2A agent (chained) ([A2A spec](https://a2a-protocol.org/latest/specification/)). But there is **no first-class delegation object** proving *whose* authority the agent carries.
- **Adoption.** Interop cited with LangGraph, CrewAI, Semantic Kernel; SDKs in Python, JS, Java, C#/.NET, Go, Rust ([A2A home](https://a2a-protocol.org/latest/)). Quantitative adoption metrics: not stated on the primary page (n.a.).
- **What it does NOT cover.** No payments (explicit — deferred to AP2/x402) ([A2A spec](https://a2a-protocol.org/latest/specification/)); no general-purpose delegation-of-authority framework beyond in-task auth; no persistent cross-org identity/reputation (that is ERC-8004); no evidence/receipt standard for completed actions ([A2A spec](https://a2a-protocol.org/latest/specification/)).
- **Layers covered:** communication; partial identity (AgentCard + JWS signing + security schemes).

## 3. AP2 — Agent Payments Protocol (Google)

- **What it is.** An open protocol for agent-led payments, delivered as an **extension of A2A and MCP**, that provides a payment-agnostic framework for users, merchants, and payment providers ([AP2 announcement, Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol); [AP2 docs](https://ap2-protocol.org/)).
- **Who governs it.** Introduced by Google (16 Sept 2025) with 60+ partners; standardization of the spec is moving into **FIDO Alliance** working groups (Agentic Authentication Technical WG and Payments Technical WG), noted as "AP2 v0.2 Release and FIDO Alliance Donation" ([AP2 docs](https://ap2-protocol.org/)).
- **Current version / status (2026).** **v0.2**; public GitHub hosts spec, docs, and SDK; "get started today" posture; more integrations in progress ([AP2 docs](https://ap2-protocol.org/)).
- **Mandates (the core mechanism).** AP2 engineers trust with **Verifiable Digital Credentials (VDCs)** — tamper-evident, cryptographically signed objects chained into a **non-repudiable audit trail** ([AP2 docs](https://ap2-protocol.org/)):
  - **Intent Mandate** — captures the user's constraints/goals (price limits, timing, conditions) before a cart exists; signed upfront for delegated ("human-not-present") tasks ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)).
  - **Cart Mandate** (a.k.a. Checkout Mandate) — an unchangeable record of exact items/price the user authorizes ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol); [AP2 docs](https://ap2-protocol.org/)).
  - **Payment Mandate** — captures the user's authorization for a specific amount bound to a finalized checkout, shared with the Credential Provider, networks, and merchant processor ([AP2 docs](https://ap2-protocol.org/)).
- **Stated principles.** Verifiable **intent, not inferred action** (addresses agent hallucination/error); role-based architecture for privacy; explicit accountability for **authorization, authenticity, accountability** ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol); [AP2 docs](https://ap2-protocol.org/)).
- **Adoption / partners.** 60+ orgs including Adyen, American Express, Ant International, Coinbase, Etsy, Forter, Intuit, JCB, Mastercard, Mysten Labs, PayPal, Revolut, Salesforce, ServiceNow, UnionPay International, Worldpay ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)).
- **Relationship to x402.** Google launched the **A2A x402 extension** ("production-ready solution for agent-based crypto payments") in collaboration with Coinbase, Ethereum Foundation, and MetaMask — bridging AP2's mandate/authorization framework to x402 on-chain stablecoin settlement ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)). Third-party analysis frames them as complementary: AP2 supplies the authorization/trust semantics, x402 the settlement rail ([Openfort agentic payments landscape](https://www.openfort.io/blog/agentic-payments-landscape); [Eco: x402 explained](https://eco.com/support/en/articles/12328618-x402-protocol-explained-how-ai-agents-pay-onchain)).
- **What it does NOT cover.** AP2's audit trail is **scoped to payment transactions** — it proves *intent to pay*, not the broader authority/telos/evidence of non-payment agent actions. It does not itself define general agent identity, discovery, reputation, or a receipt for arbitrary (non-commerce) actions ([AP2 docs](https://ap2-protocol.org/)).
- **Layers covered:** payment; evidence (payment-scoped); partial delegation (mandate = scoped authorization for a purchase).

## 4. x402 — Coinbase HTTP 402 payments

- **What it is.** A payments protocol built on HTTP, reviving the `402 Payment Required` status code; open, chain-agnostic, trust-minimizing, gasless for client and resource server ([x402 GitHub](https://github.com/coinbase/x402); [x402.org](https://www.x402.org/)).
- **Who governs it.** Maintained in the **coinbase/x402** repo (Apache-2.0); stated principle that "the x402 protocol will never force reliance on a single party," but no named foundation/governing body on the repo beyond Coinbase and its CONTRIBUTING/acceptance criteria ([x402 GitHub](https://github.com/coinbase/x402)). x402.org landing page states it is an "open, neutral standard" but names no governance body ([x402.org](https://www.x402.org/)).
- **How the flow works.** Client requests a resource → server returns **402 + `PaymentRequirements`** → client builds a **Payment Payload** per the chosen `scheme`/`network` and resends with an **`X-PAYMENT`** header → resource server verifies (locally or via a **facilitator** `/verify`) → settles (directly or via facilitator `/settle`) → returns 200 with **`X-PAYMENT-RESPONSE`** (settlement details) ([x402 GitHub](https://github.com/coinbase/x402)).
- **Facilitators.** Third-party services that verify and settle on-chain payments so a resource server needs no blockchain node or wallet; expose `/verify`, `/settle`, `/supported` (scheme+network pairs) ([x402 GitHub](https://github.com/coinbase/x402)).
- **State of ecosystem (mid-2026).** Repo is at "V1 Protocol," first scheme `exact` on EVM chains, EIP-3009-compliant ERC-20 transfers; repo metrics: ~4.2k stars, 88 contributors, "used by 239," 763 forks ([x402 GitHub](https://github.com/coinbase/x402)). ERC-8004 registration files carry an `x402Support` flag and a `proofOfPayment` field in feedback, showing x402 is being wired into the on-chain agent economy ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004)).
- **Relationship to AP2.** No mention of AP2 in the Coinbase repo itself (n.a. from primary repo). The bridge is Google's **A2A x402 extension**, built with Coinbase/EF/MetaMask ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)). Analysis: x402 = agent-to-agent / agent-to-API, permissionless, settlement-trust; AP2 = agent-to-merchant / human-delegated, authorization-trust ([DEV: AP2 vs x402](https://dev.to/noopy420/google-ap2-vs-x402-the-two-protocols-competing-to-power-ai-agent-payments-5e9j); [Eco: x402 explained](https://eco.com/support/en/articles/12328618-x402-protocol-explained-how-ai-agents-pay-onchain)).
- **What it does NOT cover.** No identity of *who* authorized the payment (trust is in on-chain finality, not user authorization semantics — this is precisely the gap AP2 fills) ([DEV: AP2 vs x402](https://dev.to/noopy420/google-ap2-vs-x402-the-two-protocols-competing-to-power-ai-agent-payments-5e9j)); no telos/evidence beyond the payment tx; no reversal (on-chain finality is by design irreversible).
- **Layers covered:** payment (settlement); evidence limited to on-chain tx hash.

## 5. Agent identity & delegation (OAuth extensions, GNAP, FIDO/passkeys, Visa/Mastercard)

### 5a. OAuth / OIDC extensions for agent delegation (IETF)
- **What exists & is mature (2026).** OAuth 2.1 (PKCE-mandatory baseline), **RFC 8693 Token Exchange** (STS pattern; `subject_token`/`actor_token`; delegation chain recorded in the `act` claim), Microsoft OBO, **DPoP** (proof-of-possession), **CAEP** (sub-second revocation), **SPIFFE/SVID/SPIRE** workload identity, and **RFC 8707** resource indicators ([Zylos: agent auth & delegated access, Apr 2026](https://zylos.ai/research/2026-04-11-agent-authentication-delegated-access-oauth-scoped-tokens/)).
- **Agent-specific drafts (still drafts, no RFC status as of Apr 2026).** `draft-klrc-aiagent-auth-01` (defines agent attestation, an `agent_assertion` grant, model-hash/runtime metadata in token requests); `draft-ni-wimse-ai-agent-identity-02` (WIMSE workload identity for ephemeral agents / agent-spawns-agent); `draft-yl-agent-id-requirements-00` (global agent ID format); `draft-aip-agent-identity-protocol-00` (verifiable identity + policy enforcement); `draft-abbey-scim-agent-extension-00` (SCIM `Agents`/`AgenticApplications` resource types) ([Zylos, Apr 2026](https://zylos.ai/research/2026-04-11-agent-authentication-delegated-access-oauth-scoped-tokens/)).
- **Known weakness.** The IETF OAuth WG documented **"delegation chain splicing"** in early 2026 — a compromised intermediary can present a valid subject_token and actor_token from different contexts and have the STS mint a properly-signed token asserting a delegation chain that never occurred; mitigation (binding subject+actor to the same auth request) is not widely enforced ([Zylos, Apr 2026](https://zylos.ai/research/2026-04-11-agent-authentication-delegated-access-oauth-scoped-tokens/)).
- **Academic anchor — Authenticated Delegation.** South, Marro, Hardjono, Mahari, Whitney, Greenwood, Chan, Pentland (MIT), *Authenticated Delegation and Authorized AI Agents* (arXiv 2501.09674, Jan 2025), extends OAuth 2.0/OIDC with three tokens — **User-ID token, Agent-ID token, Delegation token** — plus a scheme to translate natural-language permissions into auditable (XACML) access-control configs, anchoring agent actions to a verifiable human principal with an audit chain ([arXiv 2501.09674](https://arxiv.org/abs/2501.09674)).

### 5b. GNAP
- **What it is.** Grant Negotiation and Authorization Protocol, a next-generation authorization protocol; **RFC 9635 (GNAP Core, Oct 2024)** and **RFC 9767 (GNAP Resource Server Connections)** ([oauth.net/gnap](https://oauth.net/gnap/); [RFC 9635 datatracker](https://datatracker.ietf.org/doc/rfc9635/)). Delegation model and explicit AI-agent applicability: not stated on the overview page (n.a. — GNAP is a general authorization protocol, not agent-specific).

### 5c. FIDO / passkeys for agents
- **What exists.** FIDO Alliance is developing **standards for trusted AI agent interactions**; AP2 spec standardization is moving into FIDO's Agentic Authentication and Payments Technical WGs ([AP2 docs](https://ap2-protocol.org/)). A dedicated "passkeys-for-agents" spec was not confirmable from a primary FIDO page in this session (n.a.).

### 5d. Visa & Mastercard identity approaches
- **Visa Intelligent Commerce (VIC) / Trusted Agent Protocol (TAP).** VIC is the umbrella program (launched Apr 2025) that authenticates AI agents, authorizes agent-initiated card transactions under scoped spend controls via a **tokenized agent credential**, and settles over fiat or a multi-chain stablecoin program; **TAP** is the specific technical protocol for how agents authenticate/authorize ([ATXP: Visa TAP explained](https://atxp.ai/blog/visa-trusted-agent-protocol-explained/); [Eco: VIC explained](https://eco.com/support/en/articles/14845484-visa-intelligent-commerce-explained); [AWS: VIC on Bedrock AgentCore](https://aws.amazon.com/blogs/machine-learning/introducing-visa-intelligent-commerce-on-aws-enabling-agentic-commerce-with-amazon-bedrock-agentcore/)).
- **Mastercard Agent Pay.** Issues an **Agentic Token** bound to an agent identity, scoped per session and per merchant; requires agents to be **registered and verified ("Know Your Agent")** before transacting; uses **Web Bot Auth (built on IETF RFC 9421)** at the CDN layer (partnered with Cloudflare) so merchants verify agent authenticity without new code ([Mastercard agentic token framework](https://www.mastercard.com/global/en/news-and-trends/stories/2025/agentic-commerce-framework.html); [Checkout.com: Know Your Agent](https://www.checkout.com/blog/mastercard-checkout-discuss-agentic-commerce-agent-pay)). **Agent Pay for Machines** (June 2026) adds credentialing, programmatic permissioning/spend limits, and guaranteed multi-rail settlement with **Verifiable Intent** ([Mastercard Agent Pay for Machines press](https://www.mastercard.com/us/en/news-and-trends/press/2026/june/mastercard-launches-agent-pay-for-machines.html)).
- **What these do NOT cover.** All are payment-network-scoped identity/authorization — they answer authority *for a transaction* within a closed network, not a neutral, cross-domain authority/telos/evidence layer for arbitrary agent actions.
- **Layers covered:** identity, delegation (via OAuth/token exchange), payment-scoped identity.

## 6. Decentralized agent trust — ERC-8004, DIDs/VCs, reputation registries

### 6a. ERC-8004 — Trustless Agents
- **What it is.** An Ethereum standard that adds an **on-chain trust layer** between agent-communication protocols (A2A/MCP) and payment rails (x402), via three per-chain singleton registries ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004); [ERC-8004 empirical study, arXiv 2606.26028](https://arxiv.org/pdf/2606.26028.pdf)):
  - **Identity Registry** — ERC-721 (+ URIStorage) NFT per agent; `agentId` resolves to an off-chain registration file (`agentURI`) declaring name, endpoints (A2A, MCP, OASF, ENS, DID, email), `supportedTrust`, and `x402Support`; portable, transferable, censorship-resistant ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004)).
  - **Reputation Registry** — signed feedback (`value`/`valueDecimals`, tags, `feedbackURI`+hash); supports revocation and appended responses; feedback can carry an x402 `proofOfPayment` ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004)).
  - **Validation Registry** — hooks for independent checks: stake-secured re-execution, **zkML** verifiers, **TEE-attestation** oracles, trusted judges ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004)).
- **Who governs it.** A Draft Standards-Track ERC (created 13 Aug 2025) authored by Marco De Rossi (MetaMask), Davide Crapis (Ethereum Foundation), Jordan Ellis (Google), Erik Reppel (Coinbase); trust model is **pluggable and tiered** ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004); [QuickNode dev guide](https://www.quicknode.com/blog/erc-8004-a-developers-guide-to-trustless-ai-agent-identity)).
- **Status (2026).** EIP status: **Draft** ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004)). Deployed to mainnet **29 Jan 2026**, with **170k+ registered agents** across Ethereum, BSC, and Base within its first months ([ERC-8004 empirical study, arXiv 2606.26028](https://arxiv.org/pdf/2606.26028.pdf)). Ethereum Foundation's decentralized-AI team has it on the 2026 roadmap ([Eco: what is ERC-8004](https://eco.com/support/en/articles/13221214-what-is-erc-8004-the-ethereum-standard-enabling-trustless-ai-agents)).
- **What it explicitly does NOT cover.** **Payments are orthogonal and out of scope** (defer to x402/stablecoins) ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004); [Eco: what is ERC-8004](https://eco.com/support/en/articles/13221214-what-is-erc-8004-the-ethereum-standard-enabling-trustless-ai-agents)). Delegation is limited to ERC-721 ownership/operator management, not authority-chain semantics ([ERC-8004 EIP](https://eips.ethereum.org/EIPS/eip-8004)). Critically, the **Validation Registry's zkML/TEE/staked-re-execution models are not implemented at the protocol level** — "still under active update and discussion with the TEE community"; and **reputation feedback is same-chain only** (no cross-chain feedback path) ([Decipher Club: what trustless agents are up to](https://www.decipherclub.com/so-what-exactly-are-trustless-agents-up-to/)).
- **Layers covered:** identity (on-chain), discovery/reputation, evidence (validation hooks — mostly unimplemented).

### 6b. W3C DIDs & Verifiable Credentials
- **DIDs v1.0** — **W3C Recommendation, 19 July 2022**, published by the Decentralized Identifier WG; defines DID syntax, data model, DID documents (public keys, service endpoints), and resolution; controller can prove control without a central registry ([W3C DID v1.0](https://www.w3.org/TR/did-1.0/)). DID 1.1 / VC 2.0 status not stated on the DID 1.0 page (n.a. from this source). DIDs+VCs+ZKPs are the substrate proposed for privacy-preserving agent IDs ([Scribd/agent-ID framework paper](https://www.scribd.com/document/884204317/Untitled-Document)) and are cited as building blocks by the Authenticated Delegation framework ([arXiv 2501.09674](https://arxiv.org/abs/2501.09674)).
- **Layers covered:** identity (decentralized), evidence (VC = signed claim).

### 6c. Agent reputation registries (ecosystem)
- Third-party reputation infra on top of ERC-8004 includes 8k4 API (IGGY-Score), Agent Arena (22,000+ agents indexed, hire via x402 micropayments), and **ERC-8183 Agentic Commerce Protocol** (Virtuals + EF dAI, Feb 2026) whose `ReputationGateHook` gates escrow funding by ERC-8004 reputation score — the most concrete production use of the Reputation Registry ([awesome-erc8004](https://github.com/sudeepb02/awesome-erc8004); [Decipher Club](https://www.decipherclub.com/so-what-exactly-are-trustless-agents-up-to/)).
- **Layers covered:** discovery/reputation, partial evidence.

## 7. Provenance & evidence — C2PA, W3C PROV, TEE attestation, transparency logs

### 7a. C2PA / Content Credentials
- **What it is.** A model for cryptographically verifiable **content provenance and authenticity** — manifests of assertions/claims with tamper-evident digital signatures bound to an asset ([C2PA Technical Spec 2.4](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html)).
- **Who governs it.** The **Coalition for Content Provenance and Authenticity (C2PA)** ([C2PA Technical Spec 2.4](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html)).
- **Status (2026).** Current version **2.4 (April 2026)**, adding a JSON serialization (crJSON), a **Repository Receipt Assertion**, an **AI Disclosure Assertion** (`c2pa.ai-disclosure`), an Environmental Sustainability Assertion, and manifest embedding into HTML/structured text ([C2PA Technical Spec 2.4](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html)). (2.2 May 2025, 2.3 Dec 2025.)
- **Identity split.** From spec v2.0 (Jan 2024) all individual/organization identity references were **removed from core C2PA** and moved to the separate **Creator Assertions Working Group (CAWG)** ([IPTC C2PA update](https://iptc.org/download/events/phmdc2025/IPTC-PHMDC-2025-Brendan_Quinn-C2PA.pdf)).
- **What it does NOT cover.** C2PA deliberately makes **no value judgment** about whether provenance is "good/bad" — only whether assertions validate and are tamper-free ([C2PA Technical Spec 2.4](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html)). It is asset/content-provenance, not an *action*-provenance or authority receipt for agent behavior.
- **Layers covered:** evidence/provenance (content).

### 7b. W3C PROV
- W3C PROV is the W3C provenance data model / recommendation family for describing entities, activities, and agents and their relationships. Direct primary-source fetch was not performed this session; treat status as the long-standing W3C PROV Recommendation (2013) — **specific 2026 status: n.a.** from a fetched source. It is a generic provenance vocabulary, not agent-action-specific.
- **Layers covered:** evidence/provenance (generic data model).

### 7c. Verifiable compute / TEE attestation for agent actions
- **What it is.** Computation whose result can be checked without re-running it — for AI, proving a specific model ran on a specific input to produce a specific output. TEE-based approach: an enclave (Intel SGX/TDX, AWS Nitro, AMD SEV-SNP) signs output with a key bound to the loaded code's measurement; a verifier (smart contract, user lib, or another agent) checks the signature against the chip vendor's attestation-chain PKI (Intel PCS, AMD KDS, AWS Nitro) ([Eco: TEEs for AI agents](https://eco.com/support/en/articles/14796365-tees-for-ai-agents-verifiable-compute); [Armalo Labs: verifiable compute](https://www.armalo.ai/labs/research/2026-05-12-verifiable-compute-tees-trust-score); [arXiv: Confidential Computing for Agentic AI](https://arxiv.org/html/2605.03213v2)). This is one of ERC-8004's pluggable Validation-Registry trust models (TEE oracle / zkML) — but **not yet implemented at protocol level** ([Decipher Club](https://www.decipherclub.com/so-what-exactly-are-trustless-agents-up-to/)).
- **Layers covered:** evidence (execution attestation).

### 7d. Transparency logs (Sigstore / Rekor) applied to agents
- **What it is.** Sigstore uses OIDC (Fulcio-issued short-lived certs) + the **Rekor** append-only transparency log; verification replays a Rekor inclusion proof against a witnessed checkpoint and matches the cert's identity claims to policy ([Sigstore security model](https://docs.sigstore.dev/about/security/); [Safeguard: Rekor deep dive 2026](https://safeguard.sh/resources/blog/sigstore-rekor-transparency-log-deep-dive-2026)). Applied to AI, Sigstore is being used for **model authenticity/transparency** (signing model artifacts) ([Red Hat: model authenticity with Sigstore](https://next.redhat.com/2025/04/10/model-authenticity-and-transparency-with-sigstore/)). Automated systems can authenticate via Workload Identity / SPIFFE SVIDs over OIDC ([Sigstore security model](https://docs.sigstore.dev/about/security/)).
- **Gap.** These log *artifacts/signatures* (supply chain), not *agent actions* in flight. A Rekor-style transparency log of agent *actions/receipts* is conceptual, not a shipped standard (n.a. for a dedicated agent-action transparency-log standard).
- **Layers covered:** evidence (append-only log of signatures).

## 8. Governance & accountability research

- **"Visibility into AI Agents" (Chan et al., 2024).** The canonical agent-visibility paper (FAccT 2024); proposes three measures — **agent identifiers, real-time monitoring, activity logging** — to make visible *where, why, how, and by whom* agents are used, to enable accountability; analyzes centralized→decentralized deployment and privacy/power-concentration tradeoffs ([arXiv 2401.13138](https://arxiv.org/abs/2401.13138)). Agent identifiers "generalize watermarks" by linking *all* of an agent's outputs (including tool use) to the agent and its user/developer/deployer ([Visibility into AI Agents, ACM PDF](https://dl.acm.org/doi/pdf/10.1145/3630106.3658948)). This is the direct antecedent of the "agent IDs" proposals.
- **Agent-ID / DID frameworks.** Follow-on work proposes unique, verifiable, privacy-preserving agent IDs via DIDs + ZKPs, an Agent-ID Provider Network, and VC issuers, with revocation lists — explicitly "inspired by the concept of IDs for AI systems outlined by Chan et al. (2024)" ([agent-ID framework paper](https://www.scribd.com/document/884204317/Untitled-Document)).
- **NIST AI Agent Standards Initiative.** Announced **17 Feb 2026**; three pillars — industry-led standards facilitation, open-source interoperability protocols (MCP + A2A as baselines, targeting an **AI Agent Interoperability Profile by Q4 2026**), and research on agent authentication/identity/security. **No enforceable agent-specific controls exist yet; first substantive deliverables not before late 2026** ([CSA: AI Agent Governance Gap, Apr 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-agent-governance-framework-gap-20260403/)).
- **Industry/enterprise frameworks (2025–2026).** CSA **Agentic Trust Framework** (zero-trust: unique identifier, credential binding, ownership chain, purpose declaration, capability manifest per agent) ([CSA Agentic Trust Framework](https://cloudsecurityalliance.org/blog/2026/02/02/the-agentic-trust-framework-zero-trust-governance-for-ai-agents)); **OWASP State of Agentic AI Security & Governance 2.0** ([OWASP GenAI](https://genai.owasp.org/resource/state-of-agentic-ai-security-and-governance/)); Microsoft **Agent Governance Toolkit** (open-source runtime security) ([Microsoft OSS blog, Apr 2026](https://opensource.microsoft.com/blog/2026/04/02/introducing-the-agent-governance-toolkit-open-source-runtime-security-for-ai-agents/)); ITU 2025 report framing three governance pillars — **inclusivity, visibility, liability** ([ITU AI Governance Report 2025](https://www.itu.int/epublications/zh/publication/the-annual-ai-governance-report-2025-steering-the-future-of-ai/en)). Vendor-CISO surveys report **92% lack full visibility into agent identities** and **95% doubt they could contain a compromised agent** ([CSA governance gap](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-agent-governance-framework-gap-20260403/)).
- **EU AI Act treatment of agents.** Agents are classified **by purpose/context of use, not by degree of autonomy** — an agent "climbs tiers" only by being pointed at a regulated use; GPAI *model* duties (Art 53/55) sit with the model provider, *system* duties with the agent provider ([RegulatoryAI: AI Agents & the EU AI Act 2026](https://www.regulatoryai.eu/ai-agents-eu-ai-act/)). High-risk agents must satisfy risk management (Art 9), technical documentation (Art 11), **traceability/record-keeping (Art 12)**, transparency (Art 13/50 — AI-generated content marked machine-readable), human oversight (Art 14), and incident reporting (Art 73); penalties up to **€35M / 7%** for Art 5 prohibited practices ([Nestr: EU AI Act & agent governance](https://nestr.io/blog/eu-ai-act-ai-agent-governance); [RegulatoryAI](https://www.regulatoryai.eu/ai-agents-eu-ai-act/)).
- **Liability regimes.** No surveyed law treats the AI system itself as a legal person; liability attaches to providers, deployers/operators, controllers, sellers ([Licentium: agentic AI liability](https://www.licentium.io/post/agentic-ai-liability-and-autonomous-decision-making)). In the EU, the **Revised Product Liability Directive (2024/2853)** treats software/AI as a product (no-fault liability) and creates a **presumption of defectiveness where required documentation is withheld** — making tamper-evident logging/audit trails a **first-order liability variable**; the proposed **AI Liability Directive was withdrawn Feb 2025** ([AgentLiability.eu: who is liable](https://agentliability.eu/articles/ai-agent-mistakes-liability-under-eu-law)). Proposals argue for a single-point **"agent operator"** as primary defendant with rights of recourse, plus legally mandated tamper-evident audit trails and evidential presumptions ([Jurisconsul: agentic law in the EU](https://www.jurisconsul.com/post/agentic-law-in-the-european-union-governing-autonomous-ai-agents)).
- **What this body does NOT provide.** Frameworks and law converge on *what should be captured* (identity, purpose, authority scope, tamper-evident logs) but there is **no shipped cross-protocol technical standard** binding these into a portable, verifiable record — the gap this project targets.
- **Layers covered:** governance (normative), partial evidence (logging requirements).

## 9. Cross-protocol accountability / audit-trail efforts

- **AGNTCY (Internet of Agents).** Open-source collective for agents to **discover each other, verify capabilities, communicate securely, and collaborate** across frameworks/orgs; components: **Agent Directory Service** (federated registry), **SLIM** (secure low-latency messaging with MLS encryption), **OASF** (agent-attribute schema spanning A2A/MCP), **Identity** (decentralized identity — identifiers, VCs, policy-based access), and **Observability & Evaluation** ([AGNTCY docs](https://docs.agntcy.org/)). Originally launched by Cisco (Mar 2025) and **donated to the Linux Foundation (July 2025)**, with Core, Identity, and Observability & Evaluation working groups and 75+ contributing companies ([Cisco: AGNTCY donation to LF](https://news-blogs.cisco.com/emea/es/2025/07/30/cisco-dona-agntcy-a-la-linux-foundation-para-construir-la-internet-de-los-agentes/)). Closest existing thing to a full cross-protocol stack (discovery + identity + messaging + observability), but **its observability is telemetry/eval, not a portable accountability receipt**, and non-goals aren't enumerated on the docs page (n.a.).
- **NANDA (MIT Media Lab).** "The Internet of AI Agents" — proposes a new **index architecture for the agentic web** (decentralized discovery/index layer); governance and 2026 production status not stated on the landing page (n.a.) ([NANDA roadmap, MIT](https://nanda.media.mit.edu/)). Addresses the **discovery/index** layer, not accountability receipts.
- **LOKA Protocol.** Proposed as a layered agent-accountability/interoperability stack in academic/whitepaper form; a primary spec/repo was **not fetched this session** — status **n.a.** from a confirmed primary source.
- **OpenTelemetry for agents (GenAI semantic conventions).** OTel's `gen_ai.*` semantic conventions (agent spans, MCP conventions) are the emerging de facto standard for agent tracing; as of mid-2026 they remain in **Development/experimental status** (Semantic Conventions ~v1.41, GenAI not yet marked stable; `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` for the latest attributes) ([OTel GenAI README, GitHub](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/README.md); [Greptime: OTel GenAI conventions](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions); [OTel: GenAI observability blog](https://opentelemetry.io/blog/2026/genai-observability/)). This is **observability (telemetry for debugging/eval), not a signed, non-repudiable accountability receipt** with authority/telos/reversal semantics.
- **Layers covered:** discovery, identity, communication, observability — but **no dedicated cross-protocol "accountability receipt" standard exists**; the closest primitives are AP2 mandate chains (payment-only), ERC-8004 feedback/validation (on-chain, mostly discovery/reputation), C2PA receipts (content), and OTel spans (telemetry).

## Gap Analysis — the five constitutional questions

Rows = the five accountability questions. For each: which protocols partially address it, and what's missing.

| Question | Partially addressed by | What each contributes | What's missing (the gap) |
|---|---|---|---|
| **(1) Authority** — under whose authority does the agent act? | AP2 Mandates ([AP2](https://ap2-protocol.org/)); Authenticated Delegation tokens (South et al.) ([arXiv 2501.09674](https://arxiv.org/abs/2501.09674)); OAuth token-exchange `act` chains + agent-auth drafts ([Zylos](https://zylos.ai/research/2026-04-11-agent-authentication-delegated-access-oauth-scoped-tokens/)); Visa TAP / Mastercard Agent Pay tokens ([Mastercard framework](https://www.mastercard.com/global/en/news-and-trends/stories/2025/agentic-commerce-framework.html)); ERC-8004 principal binding ([ERC-8004](https://eips.ethereum.org/EIPS/eip-8004)) | AP2 proves user intent-to-pay; delegation tokens link agent action to a verifiable human principal with an audit chain; ERC-8004 binds an agent's operational address to the principal it represents | **No neutral, cross-protocol delegation object** portable across MCP/A2A/payments. Authority is fragmented: payment-scoped (AP2/Visa/MC), resource-scoped (MCP RFC 8707), or on-chain (ERC-8004). Delegation-chain splicing weakness unresolved ([Zylos](https://zylos.ai/research/2026-04-11-agent-authentication-delegated-access-oauth-scoped-tokens/)). Agent-identity IETF drafts are pre-RFC. |
| **(2) Material burden** — what obligation/cost/risk does the action create? | AP2 mandate constraints (budget caps, spend limits) ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)); Mastercard/Visa programmatic spend controls ([Mastercard Agent Pay for Machines](https://www.mastercard.com/us/en/news-and-trends/press/2026/june/mastercard-launches-agent-pay-for-machines.html)); EU liability documentation duties ([AgentLiability.eu](https://agentliability.eu/articles/ai-agent-mistakes-liability-under-eu-law)) | AP2/Visa/MC encode *financial* burden (budget, per-merchant/per-session limits); EU PLD makes documentation a liability variable | **Burden is only expressed for payments.** No standard for non-financial burdens (legal obligation, resource consumption, downstream commitments, third-party impact). No machine-readable "material burden manifest" attached to a general action. |
| **(3) Telos** — what purpose/goal does the action serve? | AP2 Intent Mandate ([AP2 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)); A2A AgentSkill/description ([A2A spec](https://a2a-protocol.org/latest/specification/)); CSA "purpose declaration" + capability manifest ([CSA Agentic Trust](https://cloudsecurityalliance.org/blog/2026/02/02/the-agentic-trust-framework-zero-trust-governance-for-ai-agents)); Chan et al. "why" visibility ([arXiv 2401.13138](https://arxiv.org/abs/2401.13138)) | AP2 captures purchase intent; AgentCard declares skills/purpose descriptively; governance frameworks call for purpose declaration | **Telos is declarative and unverified.** AgentCard skills and CSA purpose declarations are self-asserted, not bound to individual actions or checked against outcomes. No standard linking a *stated purpose* to a *specific action* to *evidence it was served*. |
| **(4) Evidence** — what proves the result/outcome? | AP2 non-repudiable mandate chain ([AP2](https://ap2-protocol.org/)); ERC-8004 Reputation + Validation registries (zkML/TEE) ([ERC-8004](https://eips.ethereum.org/EIPS/eip-8004)); C2PA content provenance ([C2PA 2.4](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html)); TEE verifiable compute ([Eco TEEs](https://eco.com/support/en/articles/14796365-tees-for-ai-agents-verifiable-compute)); Sigstore/Rekor transparency logs ([Sigstore](https://docs.sigstore.dev/about/security/)); OTel GenAI spans ([OTel GenAI README](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/README.md)) | AP2 proves the *payment*; C2PA proves *content* provenance; TEE proves *a model ran on an input*; Rekor proves *a signature was logged*; OTel gives telemetry; ERC-8004 validation is the closest to action-evidence | **No unified action-evidence receipt.** Each proves a fragment (payment / content / execution / signature / telemetry). ERC-8004's zkML/TEE validation is **spec'd but not implemented at protocol level** ([Decipher Club](https://www.decipherclub.com/so-what-exactly-are-trustless-agents-up-to/)); OTel is experimental and for debugging, not non-repudiation. No standard tying *evidence-of-outcome* to *authority* and *telos*. |
| **(5) Challenge / reversal** — who can contest or undo the action? | ERC-8004 feedback revocation + appended responses ([ERC-8004](https://eips.ethereum.org/EIPS/eip-8004)); AP2 dispute-resolution audit trail ([AP2](https://ap2-protocol.org/)); CAEP real-time revocation ([Zylos](https://zylos.ai/research/2026-04-11-agent-authentication-delegated-access-oauth-scoped-tokens/)); card-network chargebacks/fraud protection ([DEV AP2 vs x402](https://dev.to/noopy420/google-ap2-vs-x402-the-two-protocols-competing-to-power-ai-agent-payments-5e9j)); EU recourse against operator ([Jurisconsul](https://www.jurisconsul.com/post/agentic-law-in-the-european-union-governing-autonomous-ai-agents)) | AP2 audit trail aids dispute resolution; ERC-8004 allows revoking/responding to feedback; CAEP revokes access; card networks provide chargebacks; EU law assigns recourse to the operator | **Reversal is off-protocol and asymmetric.** CAEP revokes *future* access, not *past* actions; card chargebacks are network-specific; x402/on-chain settlement is **final by design** (no reversal). No standardized "who can challenge, on what grounds, with what evidence, to reverse" primitive spanning protocols. Legal recourse exists but is not machine-actionable. |

## Synthesis for the proposed layer

The stack today is **strong on communication (MCP, A2A), payment (AP2, x402, Visa/MC), and identity/discovery (ERC-8004, DIDs, AgentCard)**, **maturing on delegation (OAuth token exchange, Authenticated Delegation, agent-auth drafts)**, and **fragmented on evidence (C2PA, TEE, Rekor, OTel — each covers a slice)** and **weak on a portable challenge/reversal primitive**.

The clearest **whitespace** for a constitutional/accountability layer:
1. A **neutral, cross-protocol authority object** (delegation record) that travels with an action across MCP tool calls, A2A messages, and payments — generalizing AP2 mandates beyond payments and binding to a verifiable principal (composing OAuth/OIDC delegation tokens + DIDs/VCs). ([arXiv 2501.09674](https://arxiv.org/abs/2501.09674); [AP2](https://ap2-protocol.org/))
2. A **signed "accountability receipt"** that unifies authority + telos + material-burden + evidence into one non-repudiable, append-loggable record — the missing piece OTel (telemetry-only), C2PA (content-only), and ERC-8004 validation (unimplemented) each gesture at. ([OTel GenAI](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/README.md); [ERC-8004](https://eips.ethereum.org/EIPS/eip-8004))
3. A **standard challenge/reversal primitive** (who can contest, grounds, evidence, effect) that is machine-actionable and protocol-neutral — no existing standard provides this; reversal is currently network- or chain-specific and often final.

**Interoperate, don't duplicate:** anchor authority on OAuth/OIDC + DIDs; reuse AP2 mandate structure for the burden/intent fields; register/discover via ERC-8004 or AGNTCY directory; carry evidence via C2PA/TEE-attestation/Rekor primitives; emit telemetry via OTel GenAI conventions; and add the genuinely missing cross-protocol **receipt + challenge/reversal** semantics on top.

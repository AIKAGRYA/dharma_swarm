### New this run — the `Automerge tier policy` reds are real, and the operator's own approval cannot clear them

The 18:00Z run framed the tier-policy reds as "false red" produced by
`cancel-in-progress` cancellations, and left an explicit test open. Both halves

red on the four approved PRs is genuine.**

**1. The cancellation artifact decays on push; it was over-weighted.**
`#1173`'s 12:09:14Z `CANCELLED` attempt — the one the 18:00Z run flagged as
possibly self-inflicted — **no longer exists in the rollup**. It was attached to
the pre-push head SHA and dropped out when this lane's 18:00Z commit landed.
`#1173` now reports 0 `CANCELLED` and 2 `SUCCESS` (18:07:15Z→18:07:23Z, 8s; and
18:08:18Z→18:08:28Z, 10s). The 18:00Z run both pushed a commit *and* edited the
PR body, and produced **no cancellation** — the second attempt started 55s after
the first finished. Across all 41 open PRs the current `CANCELLED` total is
**24, every one of them on `Automerge tier policy`** (down from 26). Because the
check completes in 8–16s, cancellation requires a second triggering event inside
that window; the observed pattern is bursts, not steady state (#1189 burned 5 in
13 minutes on 08-02; #1151, #1181 and #1184 have exactly 1 each). The
concurrency question is still worth a ruling, but it is a *presentation* issue
with a decaying half-life, not the queue's main blocker.

**2. The four approved-but-red PRs fail for a structural reason.** Reading the
failing job logs directly:

- **#1118** — `tier0 needs 1 decorrelated APPROVED review(s) (family != author
  family 'unknown:app/github-actions'); have 0: []`
- **#1149** — `tier1 needs 2 decorrelated APPROVED review(s) (family != author
  family 'unknown:app/devin-ai-integration'); have 0: []`
- **#1151** — `tier2 needs 2 decorrelated APPROVED review(s) (…); have 0: []`
- **#1153** — same tier1 quorum violation **plus** `tier1 diff ceiling exceeded:
  1082 > 600 changed lines — split the PR or take the operator route`

All four carry `reviewDecision = APPROVED`, and in every case the sole approval
is from the repo owner **`AmitabhainArunachala`**. The stale-review hypothesis
does not explain it: `latest_approvals()` only counts approvals whose
`commit_id == head_sha`
(`scripts/governance/check_automerge_tier_policy.py:136-161`), and for **#1118**
and **#1149** the owner's approval `commit_id` **equals** the current head
(`fce69236…`, `c02ce40f…` respectively). #1151 and #1153 *are* additionally
stale (`00d2cefb…` ≠ `ab3e4c76…`, `461d9ba9…` ≠ `73cf7fe7…`).

The actual cause is the reviewer-family table:

```
scripts/governance/automerge_tier_policy.json
  reviewer_families:
    chatgpt-codex-connector[bot]        -> openai
    copilot-pull-request-reviewer[bot]  -> github-copilot
```

`AmitabhainArunachala` is **not in `reviewer_families`**, so
`families.get(login)` returns `None` and the approval is skipped by the
`if family is None: continue` branch (`check_automerge_tier_policy.py:284-286`)
before any decorrelation test runs. That is why the report reads `have 0: []`
rather than listing a filtered-out approval.

**Consequence: the operator's own approval currently contributes zero to the
automerge tier quorum on every PR.** The unattended lane is satisfiable only by
`chatgpt-codex-connector[bot]` or `copilot-pull-request-reviewer[bot]`
approvals. Whether that is the intended design — automerge reserved for
bot-reviewed changes, humans taking the operator route instead — or an omission
in the table is an **operator ruling**, not an ops-lane call. Either way the
four PRs are not flaky and will not clear themselves.

**3. Secondary observation — author-family lookup is un-normalized.** Reviewer
logins go through `_normalize_login()` (`:275-276, :283`) but the author does
not: `author_family = policy["author_families"].get(author, f"unknown:{author}")`
(`:278`). The author value arrives as `app/github-actions` /
`app/devin-ai-integration` (from `gh pr view --json author`), while
`author_families` is keyed `github-actions[bot]` / `devin-ai-integration[bot]`.
The keys never match, which is why every App-authored PR reports
`unknown:app/<slug>`. This does not change the four outcomes above (reviewer
lookup already fails first), but it means the **same-family exclusion is inert
for App-authored PRs** — a Codex-connector approval on a Codex-authored PR would
not be excluded, because the author's family never resolves to `openai`. That is
a decorrelation *safety* gap, and it is the more consequential of the two.

## What it claims

This PR claims it “saturates runtime boundary adapters” by making several runtime surfaces (TaskBoard, MessageBus, ToolRegistry, RuntimeArtifactStore) able to **require** an `ExecutionIdentity` and fail closed before side effects when identity is missing. It also claims it records identity/receipt evidence in a `RuntimeStateStore`, including idempotency-before-send on MessageBus send paths and receiver-side receipt recording.

It further claims improved linkage between artifacts and trace/run context by propagating `trace_id` from `ArtifactManifest` into `ArtifactRecord`, and by recording artifact write receipts (`artifact_written`) tied to the execution identity.

## External grounding

### Palantir Foundry Ontology: stable identifiers + typed operational layer

Palantir’s Foundry Ontology is explicitly an *operational layer* with both semantic elements (objects, properties, links) and kinetic elements (actions, functions, dynamic security). ([Palantir Ontology overview](https://palantir.com/docs/foundry/ontology/overview/))

Foundry’s object model is sharply separated into *object types* (schema) and *objects/object instances* (records), with object sets as collections; the Ontology is meant to map concepts to underlying data rather than being only an abstract model. ([Palantir object types overview](https://palantir.com/docs/foundry/object-link-types/object-types-overview/))

Foundry’s API uses **stable identifiers** and explicit “API names” for types, plus a system-wide “RID” concept for resources; object type definitions include primary keys and a lifecycle/status model (ACTIVE/ENDORSED/EXPERIMENTAL/DEPRECATED). ([Palantir Get Object Type API](https://palantir.com/docs/foundry/api/ontology-resources/object-types/get-object-type/))

**Relevance to this PR:** `ExecutionIdentity` is being treated as a cross-surface identifier for “who/what/which run did this” and the PR is attempting to make runtime actions fail-closed unless identity is present in “required mode.” That direction is consistent with Palantir’s emphasis on explicit identifiers and operational semantics, but the PR’s identity model is not yet comparable to Foundry’s typed resources (RID/APIName + primary keys + status + governance semantics).

### Provenance and responsibility: W3C PROV as a rigor baseline

W3C PROV formalizes provenance in terms of **Entity**, **Activity**, and **Agent** and relations such as usage and generation (entities are used/generated by activities, which may be attributed/associated with agents). ([W3C PROV-DM](https://www.w3.org/TR/prov-dm/))

PROV also defines “bundles” as entities to enable provenance-of-provenance, i.e., trust in the provenance record itself. ([W3C PROV-DM](https://www.w3.org/TR/prov-dm/))

**Relevance to this PR:** `RuntimeStateStore` receipts and identity recording are an implicit provenance system. But the PR currently records receipts with ad-hoc strings (e.g., `task_created`, `artifact_written`, `message_consumed`) and does not yet specify a PROV-like schema (Entity/Activity/Agent typing, generation/usage separation, responsibility/association with roles, or provenance-of-provenance).

### Distributed trace propagation: W3C Trace Context as minimal interoperability bar

W3C Trace Context standardizes `traceparent` with a `trace-id` and `parent-id` (span id), plus `tracestate` for vendor-specific data, and specifies validation rules and interoperability expectations. ([W3C Trace Context](https://www.w3.org/TR/trace-context/))

**Relevance to this PR:** the PR propagates `trace_id` from manifests into records and tries to align trace/run linkage across surfaces. However, the project’s `trace_id` does not appear to be explicitly defined as W3C `trace-id` compatible (length/hex constraints) or integrated with a parent/child span model.

### Durable execution + idempotency: what “adult systems” actually do

Temporal frames idempotency as a core requirement under retry semantics (“at least once”) and highlights using idempotency keys plus durable event history to avoid duplicating side effects. ([Temporal: Idempotency and durable execution](https://temporal.io/blog/idempotency-and-durable-execution))

Restate documents a concrete operational contract: clients can supply an `Idempotency-Key` header; Restate persists the response for a retention period (default 24 hours) and replays the stored result instead of re-executing. ([Restate HTTP invocation docs](https://docs.restate.dev/services/invocation/http))

**Relevance to this PR:** the PR introduces idempotency-before-insert logic in `MessageBus.send` when `RuntimeStateStore` is available, which is directionally aligned with Temporal/Restate patterns. But the system does not yet specify retention policy, eviction, key collision scope, or a first-class “invocation lifecycle” equivalent.

## Gaps surfaced

1. **No typed ontology / stable resource identity comparable to Foundry RIDs.** The PR’s `ExecutionIdentity` is an internal carrier spread across metadata dicts; it is not a typed resource with globally stable identifiers, lifecycle, or API contracts comparable to Foundry’s resource identifiers (RID) and “API names” for types. ([Palantir Get Object Type API](https://palantir.com/docs/foundry/api/ontology-resources/object-types/get-object-type/))

2. **Receipts are not a standards-grade provenance model.** Receipts approximate provenance, but there is no explicit model mapping receipts to PROV’s Entity/Activity/Agent, nor clear semantics separating “generation” vs “usage,” nor provenance-of-provenance for the receipts themselves. ([W3C PROV-DM](https://www.w3.org/TR/prov-dm/))

3. **Trace semantics are underspecified versus W3C Trace Context.** `trace_id` propagation is added, but there is no explicit conformance story (format validation, parent/child correlation, or interop with `traceparent`/`tracestate`). ([W3C Trace Context](https://www.w3.org/TR/trace-context/))

4. **Idempotency has no declared contract or lifecycle/retention policy.** Temporal/Restate describe explicit operational semantics under retries (including how long dedupe state is retained and what the key namespace is). This PR implements dedupe behavior but does not define retention/cleanup, collision domains, or “result replay” semantics outside MessageBus. ([Temporal: Idempotency and durable execution](https://temporal.io/blog/idempotency-and-durable-execution)) ([Restate HTTP invocation docs](https://docs.restate.dev/services/invocation/http))

5. **Governance/security (a Palantir Ontology kinetic pillar) is not represented.** Palantir’s Ontology stresses kinetic elements including “dynamic security” and governance for changes; this PR adds fail-closed identity but does not define authorization semantics, policy evaluation, or auditability guarantees at the identity boundary. ([Palantir Ontology overview](https://palantir.com/docs/foundry/ontology/overview/))

## Adversarial questions

1. What is the **formal contract** for `ExecutionIdentity` fields (allowed formats, required invariants, uniqueness scope), and what prevents silent key collisions across agents/sessions/runs?

2. If `require_identity=True` is a “fail-closed” mode, what is the **migration plan** to ensure legacy call sites don’t silently keep running “identity-optional” forever (i.e., how does this become enforced rather than opt-in)?

3. What is the system’s equivalent of an “invocation lifecycle” (started/running/completed/failed/canceled) and how is it stored/replayed? How does this compare to durable execution systems’ explicit invocation IDs and retention? ([Restate HTTP invocation docs](https://docs.restate.dev/services/invocation/http))

4. How are `trace_id` and `run_id` related (1:1? many:1?), and is `trace_id` intended to be compatible with the 16-byte lowercase hex `trace-id` in W3C Trace Context? ([W3C Trace Context](https://www.w3.org/TR/trace-context/))

5. Do the recorded receipts form a **verifiable audit log** (tamper-evident, attributable, time-ordered), or are they merely internal debugging artifacts? If audit log, what is the trust model / provenance-of-provenance? ([W3C PROV-DM](https://www.w3.org/TR/prov-dm/))

## Recommended next move

This PR is useful as “plumbing” (it tightens identity propagation and introduces preflight fail-closed behavior and some idempotency patterns), but it does **not** yet justify any claim of being “Palantir Ontology-like” beyond a superficial “identity everywhere” motif. Merge only if the program explicitly commits to the next step: define a typed, governed provenance/identity schema (close to PROV + Trace Context interoperability constraints) and a non-optional enforcement plan (CI gating / adoption metric) so that this does not remain an opt-in side-channel.

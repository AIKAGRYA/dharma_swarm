# Grounding Report — PR #409: “feat(ontology): OMS hardening — TypeStatus lifecycle, api_name, uniqueness guard”

- Artifact: PR #409 — “feat(ontology): OMS hardening — TypeStatus lifecycle, api_name, uniqueness guard” ([GitHub PR](https://github.com/AmitabhainArunachala/dharma_swarm/pull/409))
- Trigger rationale: touches `dharma_swarm/ontology.py` meta-schema (ObjectType lifecycle + identifier) and registry invariants.

## What it claims (evidence-only)

This PR introduces a new lifecycle enum (`TypeStatus`) for ontology object types with values `EXPERIMENTAL`, `ACTIVE`, and `PROMOTED`, and uses it to default new types to `EXPERIMENTAL` while marking the built-in “domain types” as `ACTIVE`.

It also introduces an `api_name` field on object types intended as a “frozen API identifier” of the form `dharma.<domain>.v<N>`, with tests asserting presence, uniqueness, and basic formatting for all domain types.

Finally, it adds duplicate-name protection in the registry (`register_type`) by raising on re-registration unless `allow_overwrite=True`, with tests covering both behaviors.

## External grounding (primary sources)

### Palantir Foundry Ontology: lifecycle statuses and API-name immutability

Palantir’s Ontology resources (object types, properties, link types, actions, interfaces) explicitly carry a *status* that communicates developmental state, and Palantir specifies values including `experimental`, `active`, `deprecated`, and `example`; **object types additionally support** `promoted` as a special trust tier. ([Palantir Foundry docs — “Statuses”](https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses))

Palantir also ties destructive-change protection to status: when a resource is `active`, it cannot be deleted and its API name cannot be changed; changing an API name is only possible for resources marked `experimental`. ([Palantir Foundry docs — “Statuses”](https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses))

### Palantir Ontology API: object types are addressed by an API name and have a release status

Palantir’s `Get Object Type` API retrieves a specific object type “with the given API name”, and the response includes both `apiName` and `status` (enum values include `ACTIVE`, `EXPERIMENTAL`, `DEPRECATED`). ([Palantir Foundry API Reference — “Get Object Type”](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/object-types/get-object-type))

### Palantir actions: edits are first-class and logged as data, including action-type version

In Foundry, action submissions are modeled as object types (“action log object types map one-to-one with action types”), and include fields such as Action RID, Action type RID, and Action type version (auto-increments each time an action type is updated). ([Palantir Foundry docs — “Action log”](https://www.palantir.com/docs/foundry/action-types/action-log))

### Standards baseline: OWL is logic-based, enabling machine-checkable consistency

OWL is a computational logic-based language where expressed knowledge can be exploited to verify consistency or make implicit knowledge explicit, and it is part of the RDF/RDFS/SPARQL stack. ([W3C — OWL overview](https://www.w3.org/OWL/))

### Peer semantic layers: “definitions as contract” + access control

dbt’s Semantic Layer positions centrally-defined metrics as a contract: change a metric definition and it is “refreshed everywhere it’s invoked” for consistency across applications, and it states the semantic layer implements access permissions mechanisms. ([dbt Developer Hub — Semantic Layer](https://docs.getdbt.com/docs/use-dbt-semantic-layer/dbt-sl))

## Gaps surfaced (concrete, Palantir/peer-grounded)

1. **Status model is incomplete vs Palantir (missing `DEPRECATED`/`EXAMPLE` and related metadata).** Palantir’s status set includes `deprecated` and `example`, and deprecated resources carry structured metadata like *deprecation reason*, *deadline*, and *replacement*, plus status-consistency rules between object types, properties, and link types. ([Palantir Foundry docs — “Statuses”](https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses))

2. **No enforcement of API-name immutability tied to lifecycle.** Palantir’s rule is explicit: API names of `active` resources cannot change; renames are allowed only for `experimental`. ([Palantir Foundry docs — “Statuses”](https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses)) This PR defines an `api_name` and describes “immutable once PROMOTED”, but does not implement registry-level enforcement for (a) active immutability, (b) promoted-specific protections, or (c) migration path when renaming is blocked.

3. **Identifier design diverges from Palantir’s API-name conventions and addressability.** Palantir’s API names are in camelCase and are used directly in API paths for object types. ([Palantir Foundry API Reference — “Get Object Type”](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/object-types/get-object-type)) The proposed `dharma.<domain>.v<N>` string is closer to a namespaced package identifier than a Palantir object-type `apiName`, which suggests the project is mixing concerns: “namespace+version” vs “API addressable objectType apiName”.

4. **No explicit versioning semantics that match Palantir’s “type version increments on update” model.** Palantir’s action log captures an “action type version” that auto-increments each time an action type is updated. ([Palantir Foundry docs — “Action log”](https://www.palantir.com/docs/foundry/action-types/action-log)) This PR adds an `ObjectType.version` integer (existing field) and an `api_name` version suffix convention, but does not define: what constitutes a “type update”, how version increments are computed, or how audit/logging captures which version was used at execution time.

5. **The system is not yet “ontology-grade” in the OWL sense (no constraints, reasoning, or consistency checks).** OWL’s value is machine-checkable consistency and inference. ([W3C — OWL overview](https://www.w3.org/OWL/)) Adding status + naming is governance hygiene, but without formal constraints (cardinality, disjointness, domain/range constraints, property restrictions) you still cannot mechanically detect schema contradictions or unsafe evolution.

## Adversarial questions (what this PR assumes but does not answer)

1. If `api_name` is intended to be “frozen”, what are the exact lifecycle rules for changes (allowed when `EXPERIMENTAL` only, blocked when `ACTIVE`/`PROMOTED`), and where is that enforced in code, not just tests?

2. What is the authoritative mapping between `ObjectType.name` (PascalCase internal symbol), `api_name` (namespaced+version string), and any external API surface (agent tools, SDK codegen, runtime calls)? Palantir uses `apiName` as the lookup key. ([Palantir Foundry API Reference — “Get Object Type”](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/object-types/get-object-type))

3. How will deprecation work (deadline, replacement, and preventing use in “user-facing apps”), given Palantir treats deprecated resources as not to be relied upon and requires structured metadata? ([Palantir Foundry docs — “Statuses”](https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses))

4. The PR adds uniqueness protection for `ObjectType.name`. Where is the equivalent protection for *api_name uniqueness across time*, including migrations, forks/branches, and “overwrite” workflows?

5. What is the audit story for schema evolution? Palantir treats edits and versions as data (action log includes action type version). ([Palantir Foundry docs — “Action log”](https://www.palantir.com/docs/foundry/action-types/action-log)) Where is the “Ontology change log” that records type status changes, api_name changes, and the actor/approval path?

## Recommended next move

This artifact is directionally aligned with Palantir’s governance primitives (status + protected identifiers), but it is still “5th grade”: it defines labels and tests without implementing the enforcement and metadata workflows Palantir relies on for safe evolution. Before building additional gates/codegen on top, require: (1) status expansion (`DEPRECATED`, `EXAMPLE`) with deprecation metadata and consistency rules, (2) hard enforcement of API-name immutability tied to lifecycle, and (3) an explicit versioning + audit trail model for schema edits comparable to Foundry’s action-log versioning.

## 6. Titanium Spine Findings

Canonical identity:

- `CorrelationContext` exists with `trace_id`, `proposal_id`, `session_id`, `cell_id` only (`dharma_swarm/correlation_context.py:52-68`). It is an optional context helper, not a canonical `ExecutionIdentity`.
- `EvidenceReceipt` exists with receipt/task/trace/claim/agent/routing fields (`dharma_swarm/spine/receipt.py:40-75`) and exports `dharma.correlation_id` as an alias (`:90-97`). This is real and test-backed.
- `invoke_agent` is a pass-through wrapper requiring an `AgentInvoker` (`dharma_swarm/spine/invoke.py:36-55`). It does not itself persist or enforce ledger writes.
- `persist_receipt` writes receipt JSON to `delegation_runs` by `task_id` (`dharma_swarm/spine/persistence.py:50-57`). That is useful, but not enough to prove one run, one receipt.

Same-name and semantic collisions:

| ID | Surfaces | Risk | Evidence |
|---|---|---|---|
| `task_id` | TaskBoard, RuntimeStateStore, A2A task id, MessageBus event task_id, spine receipt | same name, multiple meanings | `task_board.py:28-35`, `runtime_state.py:43-58`, `a2a_server.py:307-337`, `receipt.py:46`. |
| `run_id` | RuntimeLifecycle `run_...`, `workflow.py` workflow IDs, `workflow_graph.py` workflow IDs, Darwin cycles | no universal generator or FK | `runtime_lifecycle.py:62-68`, `workflow.py:267-338`, `workflow_graph.py:243-261`, `evolution.py:1986-2130`. |
| `trace_id` | CorrelationContext, TaskBoard, A2A, RuntimeStateStore, spine receipt | optional in some paths | `correlation_context.py:52-68`, `task_board.py:28-35`, `a2a_server.py:307-337`, `receipt.py:42`. |
| `claim_id` | Orchestrator metadata and RuntimeStateStore | not present as first-class TaskBoard field | `runtime_state.py:43-58`, `orchestrator.py:2002-2035`. |
| `event_id` | RuntimeEnvelope, MessageBus, BoardEventLog | multiple generators/envelopes | `runtime_contract.py:40-81`, `message_bus.py:63-73`, `board/event_log.py:61-81`. |
| `receipt_id` | Spine EvidenceReceipt and closure_v0 EvidenceReceipt | same class name, different semantics | `spine/receipt.py:36-75`, `operator_core/closure_v0.py:62-80`, `ACTIVE_SURFACE_MANIFEST.yaml:720-736`. |

Durable runtime ledger:

`RuntimeStateStore` is the best candidate. It owns `sessions`, `task_claims`, `delegation_runs`, leases, artifacts, context bundles, operator actions, and session events (`runtime_state.py:31-206`). `RuntimeLifecycle` writes claims, delegation runs, and artifacts into it (`runtime_lifecycle.py:105-235`).

It is not titanium standard yet because:

- It is not the only task/run source.
- It does not force a canonical identity object at constructors.
- A2A task IDs are not durably mapped to runtime run IDs.
- Message delivery and graph checkpoints can proceed outside it.
- Self-modification proposal/gate/apply/verify/revert receipts are not first-class ledger events.

Missing critical receipts:

- Side-effect intent receipt before every file/tool/ontology/external mutation.
- Durable A2A task receipt mapped to internal run/task.
- Message consumed/idempotency consumed receipt before handler side effects.
- Self-modification proposal/gate/apply/verify/promote/revert receipt chain in `RuntimeStateStore`.

## 10. Pillar Relations

How they currently relate:

- Ontology is local business truth, but `execute_action` does not enact all declared action semantics.
- RuntimeStateStore is intended execution truth, but TaskBoard, MessageBus, checkpoints, A2A memory, and ledgers still hold lifecycle-critical facts.
- Graph runtime is custom and local; it owns control flow but also persists full checkpoint state.
- MessageBus is the actual clean-main transport; NATS is absent/not hot path.
- A2A is external interop; it does not yet durably map external task IDs to internal run IDs.
- MCP/tool access is available but not forced through execution identity/ledger.
- Swarm/Orchestrator do internal agent routing and should sit above the spine, but currently they still own much of the execution path.
- Self-modification is a vertical mutation loop and should be ledgered like any other side effect; today it is only partially closed.

How they should relate:

Ontology owns business truth. RuntimeStateStore plus spine receipts owns execution truth. Graph runtime owns local deterministic control flow. MessageBus/NATS owns transport only. A2A owns external protocol only. MCP owns tool/data access only. Swarm owns coordination only. Self-modification owns proposal/gate/apply/verify/promote/revert, but every mutation must carry `ExecutionIdentity` and ledger receipts.

## 16. Industry Gap Analysis

Layer ownership: The target layers are named, but actual runtime layers still overlap. Production systems normally force ingress through a canonical run/task constructor and reject missing identity at boundaries.

State boundaries: Business state and execution state are distinguishable in design, but enforcement is incomplete because ontology actions can log success without mutation and runtime state is split.

Identity integrity: `trace_id` and `correlation_id` are present, but not mandatory across all surfaces. A production system needs a single `ExecutionIdentity` propagated by constructors, schemas, and tests.

Durable execution: RuntimeStateStore is a good base, but graph checkpoints, TaskBoard, MessageBus, A2A memory, and JSONL logs still hold separate truths.

Idempotency: There are idempotency fields in some subsystems, but no universal "check before side effect" invariant.

Event schema governance: `RuntimeEnvelope`, MessageBus events, BoardEvents, and spine receipts are separate. There is no single event envelope for internal transport.

Ontology governance: Telos gate enforcement is real. Domain mutation enforcement is not yet real because `modifies` and approval are declarative.

Agent interoperability: A2A gateway and cards exist, but task status is not durable and external task IDs are not cleanly joined to internal runs.

Observability: The repo has rich receipts and ledgers, but they are not yet one chain of custody.

Testing: Good targeted tests exist, including 147 tests passing in this audit. Missing tests: duplicate message delivery, crash-after-claim, restart resume, A2A restart, side-effect idempotency, self-mod verification failure rollback ledger.

Security: A2A API-key enforcement is real; broader tool/action authorization is incomplete. Local/dev bypasses need strict scoping.

Backpressure/recovery: MessageBus and workflows lack production-grade lease/claim/DLQ semantics.

Migration strategy: The convergence vector is positive, but current `ACTIVE_TRACK.yaml` still says adoption work remains.

## 18. Three Refactor Targets

### Target 1 - Make ExecutionIdentity mandatory and make RuntimeStateStore the ledger

Problem: identity exists as optional `CorrelationContext`, spine receipts, task IDs, run IDs, claim IDs, and A2A IDs, but no constructor-enforced canonical identity joins them.

Why it matters: without identity, the system cannot prove which task, event, agent, artifact, side effect, and parent run belong together.

Files affected: `correlation_context.py`, `runtime_state.py`, `runtime_lifecycle.py`, `spine/receipt.py`, `spine/invoke.py`, `orchestrator.py`, `task_board.py`, `a2a/a2a_server.py`, `a2a/node_gateway.py`, `message_bus.py`, `handoff.py`, `evolution.py`.

Target architecture: `ExecutionIdentity` becomes the canonical value object. RuntimeStateStore stores run/task/claim/message/artifact/proposal receipts. A2A and MessageBus map external IDs to this identity, not ad hoc fields.

Migration steps: add identity class; adapt `RuntimeLifecycle`; require identity in Orchestrator dispatch path; bridge TaskBoard/A2A with compatibility metadata; add ledger receipt APIs; add tracer test.

Risks: broad call-site churn; must keep old tasks readable.

Tests required: identity constructor; A2A mapping; orchestrator run receipt; artifact link; duplicate idempotency; parent/child trace.

Success criteria: one tracer task can be reconstructed from ingress to artifact by `run_id` and `trace_id`; no dispatch can occur without identity.

### Target 2 - Turn ontology actions into a real tollbooth

Problem: `ActionDef.modifies` and `requires_approval` are declared but not enforced by `execute_action`.

Why it matters: the ontology cannot be business truth if actions log success without applying approved domain mutations.

Files affected: `ontology.py`, `ontology_hub.py`, `telic_seam.py`, `logic_layer.py`, `tests/test_ontology_telos_hardwire.py`, `tests/test_ontology_registry.py`.

Target architecture: `execute_action` validates gate/approval, applies `modifies`/`creates` atomically, writes an action receipt, and fails closed on unapproved mutation.

Migration steps: define action payload shape; implement modify/create application; add approval state; add rollback or no-partial-mutation behavior; make TelicSeam explicitly projection-only.

Risks: existing tests may depend on action log-only behavior.

Tests required: action modifies object; action creates object; requires approval blocks; failed gate leaves object unchanged; hub reload preserves action/object consistency.

Success criteria: no action can log success unless domain mutation semantics were applied or explicitly declared no-op.

### Target 3 - Collapse event/checkpoint duplication into one envelope and bounded state rule

Problem: RuntimeEnvelope, MessageBus events, BoardEvent, spine receipts, and graph checkpoints are separate. Workflow checkpoints can store full outputs.

Why it matters: duplicate envelopes and unbounded checkpoints make recovery, replay, and dedupe unreliable.

Files affected: `runtime_contract.py`, `message_bus.py`, `board/event_log.py`, `workflow.py`, `workflow_graph.py`, `durable_execution.py`, `session_ledger.py`, `spine/persistence.py`.

Target architecture: one internal event envelope with `ExecutionIdentity`, schema version, event ID, correlation/causation, idempotency key, timestamp, and payload reference. Graph checkpoints store references and compact deltas.

Migration steps: define envelope; wrap MessageBus publish/consume; add idempotency table; add checkpoint size tests; mark old checkpoint formats as legacy.

Risks: migration of old checkpoint files and event consumers.

Tests required: duplicate message delivered once; crash-after-claim simulation; checkpoint size ceiling; schema version rejection; replay from references.

Success criteria: receivers dedupe before side effects, and graph checkpoint payloads are bounded.
